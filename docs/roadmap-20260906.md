# Nezha ROM roadmap — September 6, 2026

This page plans how the workspace moves from a guarded, user-confirmed booting
bring-up to a maintainable Evolution X release for the Xiaomi 17 Ultra. It
separates what is verified today from what remains, and orders the remaining
work by what unblocks the most. The [workspace status](workspace-status.md)
stays the source of the selected baseline; this page does not change any
admission, readiness flag or device authorization.

## Where the project stands

| Area | Verified today | Gap |
| --- | --- | --- |
| Android product | Authored `lineage_nezha` user/userdebug targets inheriting the full Evolution telephony product; no GSI or borrowed common tree. | Continue device integration in this tree. |
| Device images | Source-built framework images, boot-image construction, signed target-files, assembled Super. The `f9e` build completed first boot with enforcing SELinux. | The tracked `BoardConfig.mk` is a restricted template; a reviewed generator derivative enables the sole `target-files-package` goal. Not a checkout-and-build workflow. |
| Kernel and modules | Exact prebuilt 4 KiB kernel, Nezha DTB/DTBO, 914 module instances with CRC-matched providers. | No validated source-built kernel or module configuration. Kernel provenance is the modified Xiaomi.eu package. |
| Vendor/ODM | Stock-derived hardware images, reviewed policy replacements, selected OEM framework components. | Most of the hardware stack is reused as whole images; required components are not independently maintainable. |
| SELinux and compatibility | Enforcing boot, source policy integration, AVB signing, Treble labeling enforced. | Five assertion sites fail strict user-policy combination with factory CIL; VINTF framework-only mode retains two skips and two warnings; runtime access unaudited per feature. |
| Recovery | Tested `working76` TWRP derivative with reproducible packaging. | Runtime is prebuilt and permissive; sideload, decryption and OTA behavior with this ROM are unqualified. |
| Reproducibility | Pinned 1,179-project source lock, 603 hash-verified source inputs, recorded inventories. | A fresh end-to-end build still depends on separately preserved private inputs, patches and a specific environment. |
| Installer / OTA | Guarded eight-image fastboot installation; construction contract already names the OTA phase and its prerequisites. | No OTA package, no update lifecycle. Super populates logical A and empties logical B, removing the old logical fallback. |

The construction contract in
[`config/nezha-rom-construction.json`](../config/nezha-rom-construction.json)
already models the three phases this roadmap has to open in order:
`target-files`, then `super`, then `ota`. The OTA phase names its own
prerequisites: validated signed target-files and image set, APK/APEX payload
signing and trust, and qualified care-map and snapshot inputs.

## Principles that carry over

- Verified facts stay separate from unresolved work. A tooling test, a compile
  or a receipt never closes a device result.
- Every build gets a fresh source/build identity and keeps its predecessor as
  rollback evidence, as the [build lessons](feature-successor-build-lessons-20260905.md) record.
- Private inputs stay hashed and ignored; nothing proprietary is redistributed.
- Phone operations need an explicit request each time. Nothing on this page
  authorizes a flash, wipe, slot change or unlock.
- Prefer measured device evidence through the
  [hardware qualification ledger](hardware-qualification.md) over inference
  from a service list.

## Workstreams

Each workstream lists its target state, the concrete steps, and the exit
criterion that lets the status page record it as done.

### A. Release workflow: one documented path from source to bundle

Target: a maintainer builds a new identity, signs it, assembles Super, produces
the eight-image bundle and its qualification summary by following one page and
one command sequence, with receipts at each step and no hand edits.

Steps:

1. Write a release runbook that records the exact sequence the `f9e` build
   used: source check against the lock, device-candidate generation with the
   construction-source contract, native preflight and `target-files-package`,
   signed reconciliation, Super assembly and readback, bundle assembly and the
   joined qualification summary. Link each step to its existing script.
2. Wrap that sequence in a single Make entry point with a `--dry-run` plan
   mode, reusing `apple_container.py`, `generate_device_tree.py`,
   `reconcile_signed_target_files.py`, `sparse_images.py`,
   `logical_partitions.py` and `experimental_flash_bundle.py`. The wrapper
   must refuse to start when the source volume has another writer, the lock
   drifts or a private input hash mismatches.
3. Promote the construction contract from the unbound v1 descriptor to a bound
   release descriptor that admits the `super` phase once the recorded native
   roles are present, keeping `ota` blocked until workstream C qualifies it.
4. Define a release artifact layout and manifest schema so every bundle,
   target-files ZIP and receipt is discoverable by identity rather than by
   dated directory name.
5. Make `make test` plus the qualification summary the offline release gate
   and record the gate result in the runbook.

Exit: a fresh identity built by following the runbook produces a bundle whose
manifest, receipts and summary validate offline without manual intervention.

### B. Reproducibility: close the private-input set

Target: a second clean machine, given the public repository plus one hashed
private archive, reproduces the deterministic target-files members.

Steps:

1. Generate an input-closure manifest that enumerates every non-upstream
   input: applied patches under `patches/`, generated device and vendor
   trees, kernel, vendor and recovery bundles by hash, signing public keys,
   tool versions and the container image digest.
2. Rehearse a clean restore on a fresh Apple Container volume or Linux host
   using only that manifest and archive, then run the workstream A wrapper.
3. Compare member hashes between the rehearsal and the recorded build; list
   the nondeterministic members explicitly rather than treating them as
   failures.
4. Document environment pins: Ubuntu release, toolchain, Repo commit,
   container runtime and the sole-writer volume rules.

Exit: a recorded clean-machine rehearsal with a member-hash comparison and an
explicit nondeterminism list.

### C. Installer and OTA lifecycle

Target: a full A/B OTA package built from the signed target-files installs from
the running ROM into the inactive slot through `update_engine`, boots, and can
roll back. A sideloadable full package installs through TWRP as the recovery
path. Stock restoration is documented and tested.

Steps:

1. Decide the slot strategy. The current Super populates logical A and empties
   logical B. Options are to keep A-only installs with a documented stock
   return path, or to populate both logical slots so the old fallback survives.
   This is a user decision; the roadmap assumes both slots populated once OTA
   updates exist, because update_engine writes the inactive slot.
2. Qualify the dynamic-partition and snapshot inputs the contract names:
   care-map generation, `super` metadata for both slots, and Virtual A/B
   snapshot behavior on this device. The recorded preflight shows snapshot
   status `none`; confirm what the stock bootloader and `snapuserd` expect.
3. Build a full OTA from the reconciled signed target-files off-device with
   `ota_from_target_files`, then verify the payload signature and metadata
   with the pinned AOSP tools before any device step.
4. Qualify the recovery path first: sideload the full package through
   `working76` when authorized, then boot and compare the installed identity.
5. Qualify the in-ROM path: install the same package through the updater,
   reboot into the other slot, verify boot and retained data, then test
   rollback to the previous slot.
6. Record a stock restoration procedure and test it once on an authorized
   session, so a failed update has a known recovery.
7. Only after full OTA works, add incremental packages and a hosted updater
   feed as a separate step.

Exit: one recorded full OTA install from the running ROM, one recorded
sideload install, one recorded rollback and one recorded stock restoration.

### D. Kernel and modules

Target: kernel and module inputs whose provenance is official firmware, and an
explicit decision on source builds backed by measurement.

Steps:

1. Switch kernel, DTB, DTBO and module input provenance from the modified
   Xiaomi.eu package to the official China firmware already intaken under the
   [factory firmware record](factory-firmware-intake.md), keeping the
   prebuilt strategy. Recompute the export and module-provider audits against
   the new inputs.
2. Build the exact GKI tag `android16-6.12-2025-06_r8` from the Android
   Common Kernel and compare its exports and CRCs with the captured Image.
   A CRC match is the precondition for any source kernel, not a boot result.
3. Attempt the vendor module build from the MiCode `popsicle-w-oss` branch
   for the Canoe platform, compare module CRCs against the captured set, and
   record what Nezha-specific pieces the public branch lacks.
4. Decide, with measurements in hand, whether a source kernel is worth the
   maintenance cost. Staying prebuilt is acceptable and is not a GSI trait.

Exit: official-firmware kernel inputs in the build, an ACK comparison record,
and a written decision on source kernels.

### E. Vendor and ODM maintainability

Target: the vendor, ODM and `mi_ext` contributions come from an inventoried
file list with per-file provenance and role, built by the ROM build rather than
copied as whole images. Proprietary HALs stay proprietary; unneeded services
are dropped deliberately.

Steps:

1. Produce a proprietary-files inventory from the factory images with hash,
   partition, role and classification for each file: required HAL, OEM
   application, policy or configuration, or removable.
2. Start with `odm` and `mi_ext`, which are smallest, and rebuild them from the
   inventory. Compare boot and the hardware ledger before and after.
3. Move the reviewed policy replacements out of image patches and into the
   device `sepolicy` source, so policy is built rather than substituted.
4. Rebuild `vendor` from the inventory last, keeping the whole-image path as a
   fallback until the rebuilt image passes the same ledger checks.

Exit: vendor, ODM and `mi_ext` built from an inventory in the device tree with
the hardware ledger unchanged or improved.

### F. SELinux, VINTF and runtime compatibility

Target: strict user-policy combination with factory CIL passes, VINTF full mode
passes with the kernel configuration, and each qualified feature has a clean
denial audit.

Steps:

1. Resolve the five assertion sites in three groups preserved in the
   [user policy record](selinux-user-integration.md) through device sepolicy
   source, not permissive domains or filtered rules.
2. Run `checkvintf` in full mode with the kernel configuration and the device
   manifest set; close the two unlevelled definition skips and two warnings
   recorded in the [Package6 validation](package6-static-validation.md) or
   document why each is expected.
3. During authorized device sessions, collect denials per feature under test
   and fold required allows into source with a test that pins each addition
   to the observed denial.
4. Run the VTS and CTS subsets that execute in the Linux build VM against the
   built images where possible, and record which suites were not run.

Exit: strict combination produces a binary, VINTF full mode passes, and the
qualified features have zero unexplained denials.

### G. Recovery

Target: TWRP for Nezha that installs this ROM's OTA packages, decrypts user
data created by this ROM, and eventually runs enforcing.

Steps:

1. Qualify `working76` against the ROM: ADB sideload, FBE decryption of
   ROM-created userdata, and installation of the workstream C full package.
2. Compare the preserved `twrp-upstream` source experiment with the
   `working76` runtime and list the exact deltas that made `working76` work.
3. Build TWRP from source with those deltas and reach parity with
   `working76` on the same ledger before it becomes the default.
4. Restore enforcing in recovery as a separate milestone once boot, touch,
   USB and logging are stable, as the working rules already require.

Exit: a source-built recovery at parity with `working76` that installs the
ROM's OTA and decrypts its userdata.

### H. Device feature closure

This continues the [remaining feature audit](package7-remaining-feature-audit-20260905.md)
queue and the open items in the [f9e installation record](package7-f9e-install-20260906.md).

1. Post-unlock validation of the installed `f9e` build: retained userdata,
   UDFPS icon geometry, shade visuals and a first
   [hardware ledger](hardware-qualification.md) session recorded against the
   installed identity.
2. Camera: the vendor CHI stack builds no per-lens logical cameras and fails
   physical-to-role mapping. The next measurement is clearing the persisted
   camera properties from a root or recovery session and re-observing the
   role map, before any further source change.
3. Android IMS provider integration, then VoLTE and VoWiFi qualification with
   a supported carrier.
4. Panel brightness, automatic brightness and the HBM policy decision.
5. Power profile and OEM charging behavior, `mi_ext` startup and overlays.
6. The rest of the daily-driver ledger: radio, audio, sensors, GNSS, NFC,
   Wi-Fi, Bluetooth, suspend and thermals.

## Sequencing

| Phase | Workstreams | Why in this order |
| --- | --- | --- |
| 0. Now | Commit the pending test consolidation; H.1 post-unlock validation. | The installed build has no post-unlock evidence yet; every later feature fix needs a measured baseline. |
| 1. Build path | A, B | Every feature fix and every OTA experiment needs a repeatable build. This removes the hand-driven generator step and closes the private-input set. |
| 2. Update path | C, G.1 | A daily-driver ROM needs updates without a wipe. Recovery qualification comes first because it is the rescue path for OTA failures. |
| 3. Hardening | F, E | Strict policy and an inventoried vendor tree make the ROM maintainable across firmware updates. |
| 4. Optional | D.2 to D.4, G.2 to G.4 | Source kernel and source recovery are quality goals, not requirements for a non-GSI ROM. D.1 provenance switch can run earlier. |
| Continuous | H | Feature closure proceeds alongside each phase as device sessions are authorized. |

## Decisions the plan needs

- Slot strategy for Super: keep A-only with a stock return path, or populate
  both logical slots for update_engine. The roadmap assumes both.
- Whether the firmware provenance switch from Xiaomi.eu to official China
  firmware happens before or after the first OTA, since it changes the kernel,
  modules and vendor inputs at once.
- Whether a source-built kernel is in scope this year or stays a measured
  option.
- The intended audience of a release: a private bundle for this device only,
  or a publishable build that must exclude every proprietary file and ship
  an installer that consumes the user's own firmware.
