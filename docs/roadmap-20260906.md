# Nezha ROM roadmap — September 6, 2026

This page plans how the workspace moves from a guarded, user-confirmed booting
bring-up to a maintainable private Evolution X build for one Xiaomi 17 Ultra.
It separates what is verified today from what remains, records the decisions
the user has taken, and orders the remaining work by what unblocks the most.
The [workspace status](workspace-status.md) stays the source of the selected
baseline; this page does not change any admission, readiness flag or device
authorization.

## Decisions taken

These were settled on September 6, 2026 and shape every workstream below.

| Decision | Choice | Consequence |
| --- | --- | --- |
| Slot strategy | Write the physical boot chain to both slots; keep Super single-copy and update through A/B. | Virtual A/B holds one copy of the logical partitions (two copies exceed Super by 3.3 GB, and stock's own metadata leaves logical B empty), so the update path is what makes iterations cheap: each candidate installs to the inactive slot in the background and falls back on boot failure until the merge. See the [detailed plans](next-steps-plan-20260906.md) for the correction. |
| Audience | Private build for the user's own device only. | No proprietary-file exclusion, no public installer, no hosted feed. Bundles, target-files and OTA packages stay under ignored `artifacts/`. Working rules on provenance, hashes and non-redistribution still apply. |
| Kernel | Build toward a custom source kernel while keeping the prebuilt kernel as a supported option. | The kernel input bundle stays the single interface into the build. A source producer must emit the same bundle so either path can be selected per build and compared. |
| Firmware provenance switch | After the update path works, delivered as one of the first OTAs. | Changing kernel, modules and vendor inputs at once is the riskiest single change; doing it as an A/B update with rollback is safer than a fastboot reflash of the only working slot. |

The construction contract in
[`config/nezha-rom-construction.json`](../config/nezha-rom-construction.json)
already models the three phases this roadmap opens in order:
`target-files`, then `super`, then `ota`. The OTA phase names its own
prerequisites: validated signed target-files and image set, APK/APEX payload
signing and trust, and qualified care-map and snapshot inputs.

## Principles that carry over

- Verified facts stay separate from unresolved work. A tooling test, a compile
  or a receipt never closes a device result.
- Every build gets a fresh source/build identity and keeps its predecessor as
  rollback evidence, as the [build lessons](feature-successor-build-lessons-20260905.md) record.
- Private inputs stay hashed and ignored. Private audience does not relax
  provenance, hashing or the rule against putting keys in the build VM.
- Phone operations need an explicit request each time. Nothing on this page
  authorizes a flash, wipe, slot change or unlock.
- Prefer measured device evidence through the
  [hardware qualification ledger](hardware-qualification.md) over inference
  from a service list.
- Design each new interface so the prebuilt and source-built variants of an
  input are interchangeable and comparable, starting with the kernel bundle.

## Workstreams

Each workstream lists its target state, the concrete steps, and the exit
criterion that lets the status page record it as done.

### A. Release workflow: one documented path from source to bundle

Target: a maintainer builds a new identity, signs it, assembles Super, produces
the flashable bundle and the OTA package and their qualification summary by
following one page and one command sequence, with receipts at each step and no
hand edits.

Steps:

1. Write a release runbook that records the exact sequence the `f9e` build
   used: source check against the lock, device-candidate generation with the
   construction-source contract, native preflight and `target-files-package`,
   signed reconciliation, Super assembly and readback, bundle assembly and the
   joined qualification summary. Link each step to its existing script.
2. Wrap that sequence in a single Make entry point with a dry-run plan mode,
   reusing `apple_container.py`, `generate_device_tree.py`,
   `reconcile_signed_target_files.py`, `sparse_images.py`,
   `logical_partitions.py` and `experimental_flash_bundle.py`. The wrapper
   must refuse to start when the source volume has another writer, the lock
   drifts or a private input hash mismatches.
3. Promote the construction contract from the unbound v1 descriptor to a bound
   release descriptor that admits the `super` phase once the recorded native
   roles are present, and the `ota` phase once workstream C qualifies it.
4. Define a release artifact layout and manifest schema so every bundle,
   target-files ZIP, OTA package and receipt is discoverable by identity
   rather than by dated directory name. Each release records its kernel
   source: prebuilt bundle identity or source-kernel producer identity.
5. Make `make test` plus the qualification summary the offline release gate
   and record the gate result in the runbook.

Exit: a fresh identity built by following the runbook produces a bundle and
OTA package whose manifest, receipts and summary validate offline without
manual intervention.

### B. Reproducibility: close the private-input set

Target: a second clean machine, given the public repository plus one hashed
private archive, reproduces the deterministic target-files members.

Steps:

1. Generate an input-closure manifest that enumerates every non-upstream
   input: the 28 Evolution patches and their JSON contracts under `patches/`,
   generated device and vendor trees, kernel, vendor and recovery bundles by
   hash, signing public keys, tool versions and the container image digest.
2. Rehearse a clean restore on a fresh Apple Container volume or Linux host
   using only that manifest and archive, then run the workstream A wrapper.
3. Compare member hashes between the rehearsal and the recorded build; list
   the nondeterministic members explicitly rather than treating them as
   failures.
4. Document environment pins: Ubuntu release, toolchain, Repo commit,
   container runtime and the sole-writer volume rules.

Exit: a recorded clean-machine rehearsal with a member-hash comparison and an
explicit nondeterminism list.

### C. Update lifecycle: both slots, then A/B OTA

Target: both slots hold a known-good build. A full A/B OTA package built from
the signed target-files installs from the running ROM into the inactive slot,
boots, and rolls back on failure. A sideloadable full package installs through
TWRP as the recovery path. Stock restoration is documented and tested once.

Steps:

1. Author the both-physical-slot delivery route. The current route writes
   seven A-chain images and a Super with logical B empty, which is the
   correct Virtual A/B layout. The new route writes the seven physical images
   to both slots so no stock boot chain remains on B and `working76` sits on
   both recovery slots; Super stays single-copy. This is a new reviewed plan
   and bundle, not a rewrite of the existing receipts.
2. Confirm the device's update mechanism from the retained stock evidence and
   the build configuration: Virtual A/B with compression is the expected mode
   for an Android 16 launch device. Record what `update_engine`, `snapuserd`
   and the bootloader expect, so step 3 builds the right package type. The
   recorded preflight shows snapshot status `none`, meaning no merge pending,
   not that snapshots are unsupported.
3. Qualify the dynamic-partition and snapshot inputs the contract names:
   care-map generation, `super` metadata for both slots and the
   `dynamic_partitions_info.txt` members of the target-files.
4. Build a full OTA from the reconciled signed target-files off-device with
   `ota_from_target_files`, then verify the payload signature, metadata and
   partition list with the pinned AOSP tools before any device step.
5. Qualify the recovery path first: sideload the full package through
   `working76` when authorized, boot and compare the installed identity.
6. Qualify the in-ROM path: install the same package through the Updater's
   local-file option or `update_engine_client`, reboot into the other slot,
   verify boot and retained data, then force a rollback to the previous slot
   and verify it still boots.
7. Record a stock restoration procedure and test it once in an authorized
   session, so a failed update has a documented recovery beyond slot fallback.
8. Only after full OTA works, add incremental packages so routine updates
   transfer less.

Exit: both physical slot chains written by a recorded route; one recorded full OTA install
from the running ROM; one recorded sideload install; one recorded rollback;
one recorded stock restoration.

### D. Kernel: design for source, keep prebuilt selectable

Target: a source-built kernel, DTB/DTBO and module set that reproduces the
captured kernel's exports and configuration, boots on the inactive slot through
an OTA, and can be swapped with the prebuilt bundle at build time.

The existing bundle interface is the anchor. `kernel/xiaomi/nezha/stock-prebuilt.mk`
consumes a bundle containing `kernel-inputs.mk`, a hashed `receipt.json`,
`kernel/Image`, `dtb/vendor.dtb`, `dtbo/dtbo.img` and three module stages.
A source producer emits the same bundle with a `source` provenance kind, so
downstream packaging, AVB, module audits and the release manifest treat the two
identically and can diff them.

Steps:

1. Extend the kernel bundle receipt schema with a provenance kind, `prebuilt`
   or `source`, and for source builds the ACK commit, vendor commit, defconfig
   hash, toolchain identity and build flags. Keep the prebuilt path unchanged.
2. Switch the prebuilt bundle's provenance from the modified Xiaomi.eu package
   to the official China firmware already intaken under the
   [factory firmware record](factory-firmware-intake.md). Recompute the export
   and module-provider audits. Deliver this as one of the first OTAs per the
   decisions table.
3. Build the exact GKI tag `android16-6.12-2025-06_r8` from the Android
   Common Kernel with the audited `gki_defconfig` and the matching Clang, and
   compare exports, CRCs and IKCONFIG against the captured Image with the
   existing readers. This is the parity gate; without it a source kernel
   cannot load the captured vendor modules.
4. Build the vendor modules from the MiCode `popsicle-w-oss` branch for the
   Canoe platform against that GKI, compare module CRCs with the 914 captured
   instances, and record which Nezha-specific pieces the public branch lacks.
   Build the DTB and DTBO from `kernel_devicetree` and compare with the
   captured overlays.
5. Package the result as a source-kind bundle, build a ROM identity with it,
   and install it on the inactive slot through the workstream C OTA path with
   the prebuilt build on the other slot as fallback. Qualify with the hardware
   ledger, paying attention to the module stages that differ.
6. Once parity holds, carry Nezha-specific kernel changes as patches on the
   pinned ACK and MiCode commits under `kernel/`, with the config audit as the
   regression check.

Exit: a source-kind bundle that passes export and CRC parity, boots on the
device via OTA, and a recorded ledger comparison against the prebuilt build.
The prebuilt bundle remains selectable and its receipts remain valid.

### E. Vendor and ODM maintainability

Target: the vendor, ODM and `mi_ext` contributions come from an inventoried
file list with per-file provenance and role, built by the ROM build rather than
copied as whole images. Proprietary HALs stay proprietary; unneeded services
are dropped deliberately.

Steps:

1. Produce a proprietary-files inventory from the factory images with hash,
   partition, role and classification for each file: required HAL, OEM
   application, policy or configuration, or removable.
2. Start with `odm` and `mi_ext`, which are smallest, and rebuild them from the
   inventory. Compare boot and the hardware ledger before and after.
3. Move the reviewed policy replacements out of image patches and into the
   device `sepolicy` source, so policy is built rather than substituted.
4. Rebuild `vendor` from the inventory last, keeping the whole-image path as a
   fallback until the rebuilt image passes the same ledger checks.

Exit: vendor, ODM and `mi_ext` built from an inventory in the device tree with
the hardware ledger unchanged or improved.

### F. SELinux, VINTF and runtime compatibility

Target: strict user-policy combination with factory CIL passes, VINTF full mode
passes with the kernel configuration, and each qualified feature has a clean
denial audit.

Steps:

1. Resolve the five assertion sites in three groups preserved in the
   [user policy record](selinux-user-integration.md) through device sepolicy
   source, not permissive domains or filtered rules.
2. Run `checkvintf` in full mode with the kernel configuration and the device
   manifest set; close the two unlevelled definition skips and two warnings
   recorded in the [Package6 validation](package6-static-validation.md) or
   document why each is expected.
3. During authorized device sessions, collect denials per feature under test
   and fold required allows into source with a test that pins each addition
   to the observed denial.
4. Run the VTS and CTS subsets that execute in the Linux build VM against the
   built images where possible, and record which suites were not run.

Exit: strict combination produces a binary, VINTF full mode passes, and the
qualified features have zero unexplained denials.

### G. Recovery

Target: TWRP for Nezha that installs this ROM's OTA packages, decrypts user
data created by this ROM, and eventually runs enforcing.

Steps:

1. Qualify `working76` against the ROM: ADB sideload, FBE decryption of
   ROM-created userdata, and installation of the workstream C full package.
2. Compare the preserved `twrp-upstream` source experiment with the
   `working76` runtime and list the exact deltas that made `working76` work.
3. Build TWRP from source with those deltas and reach parity with
   `working76` on the same ledger before it becomes the default.
4. Restore enforcing in recovery as a separate milestone once boot, touch,
   USB and logging are stable, as the working rules already require.

Exit: a source-built recovery at parity with `working76` that installs the
ROM's OTA and decrypts its userdata.

### H. Device feature closure

This continues the [remaining feature audit](package7-remaining-feature-audit-20260905.md)
queue and the open items in the [f9e installation record](package7-f9e-install-20260906.md).

1. Post-unlock validation of the installed `f9e` build: retained userdata,
   UDFPS icon geometry, shade visuals and a first
   [hardware ledger](hardware-qualification.md) session recorded against the
   installed identity.
2. Camera: the vendor CHI stack builds no per-lens logical cameras and fails
   physical-to-role mapping. The next measurement is clearing the persisted
   camera properties from a root or recovery session and re-observing the
   role map, before any further source change.
3. Android IMS provider integration, then VoLTE and VoWiFi qualification with
   a supported carrier.
4. Panel brightness, automatic brightness and the HBM policy decision.
5. Power profile and OEM charging behavior, `mi_ext` startup and overlays.
6. The rest of the daily-driver ledger: radio, audio, sensors, GNSS, NFC,
   Wi-Fi, Bluetooth, suspend and thermals.

## Sequencing

| Phase | Workstreams | Why in this order |
| --- | --- | --- |
| 0. Now | Commit pending work; H.1 post-unlock validation. | The installed build has no post-unlock evidence yet; every later feature fix needs a measured baseline. |
| 1. Build path | A, B, D.1 | Every feature fix, every OTA and every kernel experiment needs a repeatable build. The kernel receipt schema change lands here so later bundles carry provenance from the start. |
| 2. Update path | C, G.1 | Both slots populated, then OTA from the running ROM. This is what makes later testing cheap: each candidate goes to the inactive slot and falls back on failure. Recovery qualification comes first because it is the rescue path. |
| 3. Provenance and kernel | D.2 to D.5 | The provenance switch is the first real OTA. Source-kernel parity and the first source-kernel boot follow, each as an update with the previous build on the other slot. |
| 4. Hardening | F, E | Strict policy and an inventoried vendor tree make the ROM maintainable across firmware updates. |
| Optional | D.6 as ongoing, G.2 to G.4 | Kernel patches on pinned sources become routine work. Source recovery is a quality goal, not a requirement. |
| Continuous | H | Feature closure proceeds alongside each phase as device sessions are authorized. |
