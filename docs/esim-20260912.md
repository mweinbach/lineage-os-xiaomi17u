# eSIM enablement attempt, 2026-09-12

**Historical first attempt.** The later
[service and modem investigation](esim-deep-20260912.md) confirms an installed
eUICC ISD-R application and accepted modem eSIM selection. It supersedes this
page's next-step restrictions and unresolved applet-presence discussion while
preserving the factory-command measurements below.

**eSIM was not enabled.** On the connected China-market `2512BPNDAC` / `nezha`
unit, Xiaomi's factory eSIM switch returned a successful transport result but
failed to obtain an EID in 30 attempts. It finished with `value=FAILED`.
Android continued to report two absent, removable SIMs, neither an eUICC.
The physical-SIM selection was restored and its recorded modem configuration
was read back byte-for-byte identical.

This session observed installed build `nezha.b2c99443fe9e90a4a7954eac` (v25),
slot A, normal Android SELinux Enforcing. That is newer than the v23 checkpoint
previously selected in the status page. The device serial matched the original
private phone baseline; serials and raw logs remain under ignored
`reports/esim-20260912/`. The sanitized receipt is
[research/esim-20260912.json](../research/esim-20260912.json).

## What was missing

| Layer | Measured result |
| --- | --- |
| Hardware identity | Model `2512BPNDAC`, `ro.boot.hwc=CN`, hardware version `5.9.0` |
| Framework features | `android.hardware.telephony.euicc` and `.euicc.mep` already declared |
| Profile manager (LPA) | No `android.service.euicc.EuiccService` implementation, including disabled components; no Google, Xiaomi or other LPA package found |
| Android eSIM controller | `UnavailableState`, `mSelectedComponent=null`, `mEuiccService=null` |
| Vendor services | QTI AIDL `IUimLpa/UimLpa0` and `UimLpa1` registered |
| Modem / card state | Two slots, both `mIsEuicc=false`, empty EID and ATR, `CARDSTATE_ABSENT`; default eUICC card ID `-2` (uninitialized) |

The LPA is a real software omission, but adding it alone does not establish a
usable chip. Android routes profile management through an LPA; the modem must
also report the eUICC through its card/slot-status interfaces, including EID.
See AOSP's [implementation guide](https://source.android.com/docs/core/connect/esim-overview)
and [modem requirements](https://source.android.com/docs/core/connect/esim-modem-requirements).

## Factory switch experiment

The user's request to inspect the device and try to enable eSIM covered this
bounded attempt. ADB was temporarily restarted as root for the stock diagnostic
tool and restored to shell UID 2000 afterward. No ROM was flashed, phone reboot
requested, app installed, profile downloaded/deleted, or userdata cleared.
Normal Android remained Enforcing.

The retained stock `/odm/etc/factory_cmd_config/modem.xml` describes the enable
and restore commands. The live `/vendor/bin/mtb` executable was SHA-256 identical to
the retained stock extraction. Its help and disassembly distinguish eSIM
selection (`5 10 1`), physical SIM2 selection (`5 10 2`), and the separate
destructive reset case (`5 10 5`). The reset case was not invoked.

1. Read and preserve the 70-byte modem
   `uim_extended_slot_mapping_config`. The separate `esim_enable` EFS read
   returned modem result `-117`; its meaning is not inferred.
2. Invoke the documented eSIM selection with diagnostic output enabled:
   `mtb 5 10 1 1`. Its SIM-type request logged values `1,3` and transport
   result `0`, followed by 30 EID reads and `get eid timeout`, `value=FAILED`.
   Transport result `0` is not proof the modem accepted an eUICC configuration.
3. Re-read Android telephony and the modem configuration. No EID, eUICC or
   additional slot appeared. Radio indications still reported absent cards.
4. Restore physical SIM2 with `mtb 5 10 2 1`. The tool logged values `1,1`,
   `SIM2 Power Up successfully`, and `value=SUCCEED`.
5. Read back the original 70-byte configuration and compare bytes. SHA-256
   remained `009e348dbb9274b0951781c24f6b2a869f5a5cd3968842a898db9efac73391a1`.
   The `esim_enable` read still returned `-117`, eSIM-related global settings
   were unchanged, and both slots returned the original absent-SIM state.

Final build, boot slot and boot-completed state matched the initial observation.
Final uptime exceeded 13 hours. ADB returned to its original non-root state.
There was no inserted SIM, so this is not a calls/data or physical-SIM acceptance
test, nor a claim that all modem storage was inventoried.

## Decision and limits

There is no working native eSIM path on this unit with its current CN modem
firmware. The evidence cannot distinguish a physically absent chip from a chip
that the CN hardware/firmware configuration does not expose. A global model's
eSIM specification is not evidence for this unit, and the vendor LPA service
names and Android feature flags do not prove the chip exists.

Do not bake in an LPA, force the eSIM Settings UI, change modem NV defaults, or
replace regional firmware as a claimed fix for this result. A new native-eSIM
experiment needs device-specific evidence for a usable chip and a supported way
to expose it. A removable eUICC in a physical SIM slot is a separate possible
route, requiring its own hardware and validation; none was present or tested.

Workspace validation: `make test-current` passed 1,124 tests and
`make test` passed 5,101. Evidence/input hashes and mapping bytes were
independently recomputed. These offline checks do not establish eSIM hardware
functionality. No new tests were added for this documentation-only change.
