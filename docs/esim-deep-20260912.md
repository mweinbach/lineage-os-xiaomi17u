# eSIM service and modem investigation, September 12, 2026

**The secure element's application directory lists the standard eUICC ISD-R
application. eSIM has not yet been enabled.** This continues the
[factory-command attempt](esim-20260912.md) on installed
v25, `nezha.b2c99443fe9e90a4a7954eac`. The earlier factory failure was insufficient
to establish whether the modem accepted eSIM selection. The direct probe now
confirms that it does: slot 2 advertises eSIM support, accepts selection, and
reports the selected eSIM type. The remaining measured failure is card startup:
the modem receives no ATR and cannot obtain an EID.

The user requested deeper decompilation and device experiments, then expressed
a preference for an original SIM application. The work therefore includes an
original, platform-signed diagnostic APK. Proprietary decompilations, firmware,
raw device logs and generated APKs remain in ignored
`reports/esim-deep-20260912/`.

## What the factory command hid

The retained `mtb` executable sends QMI UIM `SET_SIM_TYPE` (`0x7a`) and frees the
response without checking the modem result/error fields. Its EID loop also
discards the useful modem error. Successful QMI transport alone was not proof
of accepted selection in the first experiment.

Direct queries use the live vendor UIM service object `(1, 118, 6)` and preserve
both transport and modem results. The native QTI RadioConfig converter resolves
the different enums:

| Meaning | Xiaomi app value | RadioConfig HAL value | QMI current type |
| --- | --- | --- | --- |
| Physical SIM | 0 | 1 | 1 |
| Integrated UICC | 2 | 2 | 2 |
| eSIM | 1 | 4 | 3 |

`GET_SIM_TYPE` (`0x7b`) returns a different enum for supported combinations.
Its values `0..6` convert to HAL capability masks `1..7`. This phone's supported
values `[2,6]` therefore mean physical+iUICC on slot 1 and
physical+iUICC+eSIM on slot 2. They are modem-advertised capabilities, not proof
of a functioning eUICC application.

The explicit request `[1,3]` returns modem result/error `0/0`. Readback changes
from `[1,1]` to `[1,3]`; Xiaomi's `uim_current_sim_type` EFS record also provides
the relevant selector readback. The older 70-byte extended-mapping record alone
was not an adequate selector check.

`GET_SLOT_STATUS` contains card state/error `(2,3)`: **ERROR / NO_ATR**.
Qualcomm's HAL deliberately converts that combination to Android's ABSENT
state. The direct EID query on slot 2 returns modem error `3` (Internal), while
slot 3 returns `94` (NotSupported).

## Stock activation path and our application

The SM8850 path resides in TeleService's `QCMiuiEsimManager`, rather than the
LPA's UI. It calls QTI `setSimType`, checks the asynchronous success status,
and reads the current-type record. The exact global implementation removes
the CN binding manager. With its measured wake configuration flags false, it
performs no additional GPIO, SIM-power or EFS operation before selection.

An optional stock wake path opens the eSE reader's logical channel for
`A000000151000000`, P2 `00`, holds it during the switch and closes it afterward.
The factory SecureElement app also has a companion broadcast handler restricted
to factory builds. Having `mtb` installed does not establish that this handler
exists in the current ROM.

A plain `app_process` invocation under UID 1000 could inspect the reader, but
could not select the channel. The installed SecureElement implementation checks
the first package associated with the caller UID for
`SECURE_ELEMENT_PRIVILEGED_OPERATION`; a numeric system UID alone is insufficient.
The original diagnostic APK uses its own package/UID, requests that standard
permission, and uses public `SEService` APIs. Its platform certificate matches
the installed platform certificate, and the actual permission grant was
verified after installation. This allowed the stock ISD channel to open.

The APK has no network permission, shared UID, boot receiver, profile deletion
or reset operation. Its externally callable activity and STOP receiver require
`DUMP`. Channel operations have a bounded deadline and close their own resources.

## Device experiments

Each failed modem experiment restored physical selection `[1,1]`. Direct power
commands use QMI slot 2 and avoid the legacy OEM86 helper's EFS write.

| Experiment | Measured result |
| --- | --- |
| Direct eSIM selection | Modem accepts `[1,3]`; selector readback confirms it; NO_ATR and no EID |
| Power down, select eSIM, power up | Both power requests succeed; NO_ATR and no EID |
| Hold stock eSE ISD channel, select eSIM | Channel opens with verified permission; modem accepts selection; NO_ATR and no EID |
| Hold channel, power cycle selected eSIM | Power requests succeed; repeated unchanged selector returns error 26 (NoEffect); NO_ATR and no EID |
| Select eUICC ISD-R over eSE, P2 `04` and `00` | Selection fails; session closes |
| Select ISD-R with modem eSIM mode selected | Same selection failure; physical selector restored afterward |
| Read stock ISD's application directory | GET STATUS returns `6985`; GET DATA `2F00` succeeds with 38 application AIDs, including exact ISD-R |
| Supply skipped terminal-capability record, hold eSE and initialize eSIM | Exact six-byte readback verified; power and selector requests succeed; NO_ATR and no EID; original record absence restored |

The P2 `00` native APDU trace is more informative than Java's
`NoSuchElementException`: MANAGE CHANNEL succeeds, SELECT of
`A0000005591010FFFFFFFF8900000100` receives status `6999`, and channel closure
succeeds. `6999` means selection failed. The Java Card specification permits it
both for no matching applet on an empty logical channel and for a matching
applet that refuses selection. It proves neither presence nor absence of the
eSIM applet. See Oracle's
[Java Card runtime specification, section 4.6.2](https://docs.oracle.com/en/java/javacard/3.2/jc-re-spec/F74157_03.pdf).

The subsequent directory query resolves applet presence: its 636-byte successful
response lists `A0000005591010FFFFFFFF8900000100`, plus two other GSMA AIDs.
The 38 minimal `61/4F` entries account for all 634 data bytes, followed by the
two-byte status. It contains no hidden lifecycle metadata. The privileged
registry query was refused with `6985`, so applet lifecycle remains unverified.
SPI access to an eSE directory is not proof of a working modem-facing eUICC
interface.

## Secure-element hardware path

Live `eSE1` is served by `android.hardware.secure_element-service.qti`, using
Qualcomm TEE libraries and the ST54 hardware helper. The executable,
`libGPQeSE`, `libEseUtils` and `libstnfc-streset` match the retained stock files.
The alternative Goodix service is not running.

The ST54 GPIO driver matches the retained module. Disassembly establishes that
ioctl `0x4004eb01` only reads the raw power/reset GPIO. The read returned `1`.
The stock device tree assigns this line to GPIO46; the NFC reset is separate.
No SIM mux operation was found in that driver. The successful stock ISD
selection is stronger evidence of a working chip transaction than the HAL's
cached presence/ATR getters.

ST's [ST54L specification](https://www.st.com/en/secure-mcus/st54l.html) describes
eSIM-capable hardware. That does not identify the secure applications installed
on this particular unit or establish the modem-facing connection.

## Original profile-manager path

The actual global LPAs are in the `mi_ext` product overlay. Their code was
studied privately; neither proprietary APK is required for the owned-app route.
Xiaomi's newer profile backend wraps standard `EuiccCardManager` operations.
An original privileged `EuiccService` can use that API for card management and
an appropriate ES9+ implementation for profile downloads. The device-specific
QTI selector belongs in a narrow, separately verified adapter.

This diagnostic app is not yet a profile manager. UI and profile APIs cannot
make the current NO_ATR failure into a working modem connection. The firmware
and application-directory investigations below determine the next concrete
hardware step.

## Firmware and runtime configuration comparison

The running `qdsp6_oemsw.mbn` and modem DTB match the retained CN firmware.
The CN QDSP build uses `kaanapali.taurimgen.prodQ`; the retained WW and newer
official EEA builds use `kaanapali.gensub6.prodQ`. Their release dates differ,
so a whole-image difference alone cannot be attributed to region.

The modem DTB is byte-identical across all three firmware sets. All UIM/eSIM
hardware records in all six hardware MCFGs also match. Comparing every MCFG
record, including numeric NV, leaves only unrelated PLMN, carrier aggregation
and trailer differences. Four actual runtime records match their defaults
byte-for-byte: `uim_hw_config`, `uim_num_of_active_slots`, `lpa_support`, and
`uim_features_status_list`.

Native comparison also finds equivalent eSIM power functions in CN and EEA,
including the 1200 mV vote and the `/pm/uim_esim/en` enable path for current
type 3. The 70-byte extended mapping is a logical/physical-slot and eUICC-port
record, not a GPIO mux table. No replacement routing configuration was derived.

## Regional initialization and the remaining boot experiment

Read-only NV item 6853 identifies this unit as product 401, hardware region 0.
The modem's OEM eSIM capability branch accepts regions 1 and 2 for this product,
so the region-0 boot skips an initialization branch. This proves a regional
software decision; it does not prove that it caused NO_ATR.

The separate legacy GPIO function has no product-401 mapping and falls back to
a generic descriptor. Its getter also configures the GPIO. It was not invoked.

The skipped initializer writes two eSIM-specific records:

| Record | Current state | Stock application-LPA initialization |
| --- | --- | --- |
| `/nv/item_files/modem/uim/lpa/lpa_support` | `01010002010000000000000000000000` | `00000100000000000000000000000000` |
| `/nv/item_files/modem/qmi/uim/terminal_capability_Subscription01` | Absent | `060083010700` |

Disassembly and modem QDB messages establish that Xiaomi EFS result `-117`
maps to the underlying missing-file error in this read path. The second record
encodes the standard `83 01 07` terminal capability required by
[AOSP's eSIM modem requirements](https://source.android.com/docs/core/connect/esim-modem-requirements).
It was tested alone with an exact readback, held stock ISD channel and SIM
power cycle. The result remained NO_ATR. The test-created file was deleted
through the verified single-file EFS operation; readback again returned `-117`.

The first record selects between modem and application LPA implementations.
It is not a simple on/off eSIM flag: byte 2 disables the modem-side LPA in the
stock application-LPA configuration. A modem service getter caches that mode
after first use. A live file write and SIM power cycle therefore cannot test
the complete global initialization. No live edit of this record was attempted.

The remaining concrete experiment is to back up the current 16 bytes, apply
both exact stock eSIM initialization records, select eSIM and reboot once so
the modem reads the new LPA mode. Native EID/ATR, QMI and Android slot state
would decide success. On failure, restore the original 16 bytes, remove only
the test-created terminal record, restore physical SIM selection and reboot
again to restore the cached mode. Product/region identity and firmware images
are not part of this experiment. It requires explicit reboot authorization
under the project's phone-operation rule and has not been performed.
