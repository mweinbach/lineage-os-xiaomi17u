**The authorized reboot experiment did not enable eSIM. The original modem

This executes the bounded experiment prepared in the

saved before either write. The live `mtb` hash matched the previously inspected
executable. Its decimal-byte write interface was used and every candidate was
read back exactly before reboot.

The test boot completed with both candidate records and eSIM selection intact.

A subsequent direct QMI slot-2 power cycle also returned successful power-down
and power-up results. Reapplying the already-selected SIM type returned

state did not improve. The final candidate snapshot was collected at a system
uptime of 353.16 seconds.

## Post-boot wake-check limitation

The phone's user remained `RUNNING_LOCKED` after reboot. The original diagnostic
APK remained installed with its SE permission granted, but its activity could
not be started before the first unlock. A separate headless attempt aborted
without reaching `READY_FOR_SWITCH`. Consequently, this session does not claim
a successful post-reboot held-channel repeat. The final direct modem power
cycle ran without a newly established hold. Successful held-channel tests from
the previous session remain separate evidence.

This limitation does not change the observed candidate configuration or native
NO_ATR result. It does limit claims about repeating every wake condition with
the application-LPA mode loaded from boot.

## Rollback and final device state

After the failed candidate, the saved original 16-byte LPA record was written
back and verified. The terminal file was checked to still contain the exact
test bytes, then only that test-created path was deleted. Its read returned
`-117`, confirming the original absence. Physical SIM selection and normal
hot-swap power handling were restored, with the original five-byte selector
record and 70-byte mapping verified before the rollback reboot.

After the second reboot, all those readbacks still matched. The modem EID query
returned its original error `3`, rather than the candidate mode's error `94`.
Three distinct observed kernel boot IDs identify the initial, candidate and
restored boots; two reboot commands were issued, as authorized.

Final checks preserve installed build `nezha.b2c99443fe9e90a4a7954eac`, slot A,
boot completed and SELinux Enforcing. ADB was returned to UID 2000. The
diagnostic app remains installed and stopped; this session's uploaded native
and headless probe files were removed. There was no profile download, deletion,
reset, firmware flash, or userdata clear.

## Result and remaining uncertainty

These two stock initialization records, including a reboot that reloads the
modem's LPA mode, are **not sufficient** to expose a working eUICC on this unit.
They should not be integrated as a verified enablement fix. This result does
not rule out every regional firmware decision or establish the remaining
electrical or secure-element OS cause.

The previous directory query still establishes the installed ISD-R applet. The
unresolved failure is its modem-facing card startup: no ATR and no usable
Android eUICC. A completed profile-management UI alone would not demonstrate
that this startup path works.
