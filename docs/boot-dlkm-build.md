# First Nezha boot and DLKM build checks

The v6 Nezha `userdebug` product **built boot, DTBO, vendor_dlkm and system_dlkm
images successfully** at `2026-08-27 22:01:05 UTC`, after 2,656 Ninja actions.
The seven requested framework policy files and the source-policy tests also
built. The [record](../research/boot-dlkm-build.json) binds this result to its
inputs, build logs, sandbox observation and output inspections.

This is a local `framework-checks` experiment, not a flashable ROM set. It
uses the existing Xiaomi.eu kernel/vendor bundles, not the newly verified
factory images. No init_boot, vendor_boot, recovery, complete root vbmeta,
target-files or OTA image was built by this probe. No phone was accessed.

The build ran in the same owning VM and preserved output directory,
`/work/out/nezha-framework-20260827T1835Z`, through its supported source-root
`out-nezha-framework-20260827T1835Z` alias. It did not resync or reset the
checkout. Actual Ninja had separate mount, network, PID and user namespaces;
source was read-only and output read-write. There was no timeout, sandbox
fallback or verification override.

## Module and selector preservation

All **381 vendor modules and 103 system modules** match the admitted input
hashes in the staging tree **and inside the built EROFS images**. This preserves
their complete bytes, including embedded signatures; it does not independently
verify signature cryptography, exported-symbol compatibility or module loading.

The vendor load list keeps 576 entries and their order, including duplicates.
The system list keeps 82 ordered entries. Stock relative paths become the
admitted basenames because build core flattens the installation directories.
Blocklist directives are preserved. Other depmod metadata is generated by the
build; its image contents match the staged output. This is not a claim that
every original stock depmod metadata file was copied unchanged.

The v6 correction is now verified inside vendor_dlkm:

```text
/vendor_dlkm/lib/modules/system_dlkm.modules.blocklist
151 bytes
SHA256 370cb88e7e8915f34e94bd6b93616f263be8a3523adc15fb554a712dc016a03f
```

That file exactly matches the stock selector and remains separate from the
vendor module blocklist. The system image also contains its generated
`modules.blocklist` with the same active directives. This preserves the
[intended ZRAM provider selection](zram-module-plan.md); no runtime loader
behavior was tested.

The first one-off image-content capture used a 16 MiB per-file ceiling, below
one admitted 20,661,360-byte module. The guarded tool correctly refused it before
publishing a capture. That failure is preserved. The follow-up uses the exact
maximum and total lengths from the hashed staging inventory, then verifies
every captured file against its expected hash and length. No tool guard or
image check was disabled.

## Policy and remaining boundaries

The build produced platform CIL, its mapping and genfs snippet, plus system-ext
and product CIL/mapping files. The four latter files are one newline each in
this minimal product: they were generated, not omitted by the verification
driver. `sepolicy_neverallows`, `sepolicy_test` and `sepolicy_dev_type_test`
passed for the selected source graph.

Those tests **do not include the captured proprietary vendor/ODM policy**.
The separate combined Evolution/factory check reaches 21 strict assertion
sites and does not produce a policy binary. A source-policy pass is therefore
not a complete compatibility or enforcing-runtime result. All assertions
remain enabled. The regenerated Java configuration also retains
`RelaxUsesLibraryCheck=false`, enabled dexpreopt and the prebuilt ELF page check.

The [factory partition metadata](partition-metadata.md) supplies package
extents, including a 32 MiB DTBO partition. This v6 build still uses its recorded
22 MiB DTBO image-length budget. It fits that local budget, but neither value
is a live capacity measurement. Full framework/vendor integration, complete
image packaging, signing policy, bootloader state and separately authorized
hardware tests remain necessary before a first device experiment.
