# Update mechanism the built ROM declares — September 6, 2026

Read-only inspection of the metadata inside the transferred `f9e` native
target-files archive (`lineage_nezha-target_files.zip`, SHA256
`cc8304be1bd04670de6505a938bdcc3f0f16e4c472f68b4f6a73df63e2803057`) and the
authored device product. No image was extracted, no build ran, and the phone
was not accessed. This settles the [roadmap's](roadmap-20260906.md) C.2 question
of what update package the ROM expects before any OTA is built.

## What the archive declares

| Field | Value | Meaning |
| --- | --- | --- |
| `ab_update` | `true` | A/B update package expected |
| `virtual_ab` | `true` | Virtual A/B: the updater writes the inactive slot's logical partitions through snapshots on userdata, then merges after a successful boot |
| `virtual_ab_cow_version` | `3` | COW format version 3 |
| `virtual_ab_compression` | absent | No compression flag; the product inherits `virtual_ab_ota/launch.mk`, not the compression variant |
| `use_dynamic_partitions` | `true` | Logical partitions in one `super` block device |
| `super_partition_groups` | `qti_dynamic_partitions` | Single group, maximum 15,290,335,232 bytes, device 15,300,820,992 bytes |
| `dynamic_partition_list` | `mi_ext odm product system system_dlkm system_ext vendor vendor_dlkm` | The eight logical images |
| `META/ab_partitions.txt` | 15 entries | `boot dtbo init_boot mi_ext odm product recovery system system_dlkm system_ext vbmeta vbmeta_system vendor vendor_boot vendor_dlkm` |
| `META/care_map.pb` | present | Care map already generated by the build |
| `META/update_engine_config.txt` | payload major 2, minor 9 | Payload format the updater will produce |
| `META/postinstall_config.txt` | absent | No post-install step configured |
| `IMAGES/super_empty.img` | present | LP metadata template for both slot suffixes |
| `avb_vbmeta_key_path` | AOSP test key | Development key; `avb_signing.py` re-signs with the local development key |

## Consequences for the roadmap

1. **Package type.** `ota_from_target_files` on the reconciled signed archive
   produces the right full package without extra flags for A/B or dynamic
   partitions. The care map and update-engine config are already inside.
2. **Both-slot route.** Virtual A/B creates the target slot's logical
   partitions itself, and Super holds only one copy: two copies of the eight
   logical images exceed the device by 3,341,697,024 bytes, and the captured
   stock metadata lists `system_b` at zero bytes. The current A-only logical
   layout is therefore the design, not a gap. What can be written to both
   slots is the seven-image physical chain, which removes the stock boot
   chain from B and puts `working76` on both recovery slots. See the
   [detailed plans](next-steps-plan-20260906.md).
3. **Snapshot state.** The recorded device preflight showed snapshot status
   `none`, which means no merge was pending. It does not say whether the stock
   bootloader and the ROM's first-stage init agree on snapshot handling; the
   first OTA test establishes that.
4. **Recovery path.** A full A/B package is also sideloadable through recovery.
   `working76` must be qualified for sideload before it is relied on as the
   rescue path.
5. **Signing.** The OTA package is signed with the same development key the
   images use. The Updater in the ROM must trust that key; the build's
   `META/otakeys.txt` and the release keys selection need checking when the
   package is built.

## What this does not establish

- That `update_engine` in the built ROM starts, accepts the payload, or merges.
- That Xiaomi's bootloader honors slot switching from the ROM's boot control
  HAL. Retained evidence shows only `ro.boot.slot_suffix=_a`.
- Compression behavior on the device; the build declares none.
- Any device result. Every item above is archive metadata and product source.
